# Task 03: i18n on tina4-js localization

## Goal

Ship a documentation site in more than one language, with the theme chrome
translated and RTL handled, without shipping every language's prose to every
reader.

## Context

tina4-js already carries a full i18n module, and it is **already inside the IIFE
bundle tina4press ships**. Verified 2026-08-05 against
`node_modules/tina4js/dist/tina4js.min.js` (27,713 bytes): `createI18n`,
`setLocale`, `loadMessages`, `relativeTime` and `isRTL` are all present. So the
runtime half of this task costs **zero additional bytes on the wire**.

The API (from tina4-js `src/i18n/i18n.ts`, confirmed against the source, not memory):

```js
const i = Tina4.createI18n({ locale, fallbackLocale, messages, rtlLocales });
i.t("nav.home");                  // dot-path AND leaf alias both resolve
i.t("welcome", { name: "Alice" }); // {placeholder} interpolation
i.number(n); i.currency(n, "USD"); i.date(d, opts); i.relativeTime(-1, "day");
i.dir();                          // "ltr" | "rtl"
await i.loadMessages("es-ES", "/i18n/es-ES.json");
i.setLocale("fr-FR");             // reactive: every t() re-renders
```

Fallback order is locale -> fallbackLocale -> the key itself, so a missing string
degrades to something readable and never throws.

### The split that matters

A static site generator must not do all of its i18n at runtime. Shipping every
language's prose to the browser would undo the weight advantage that motivated
tina4press. So:

| Layer | Where it happens | Why |
|---|---|---|
| **Page content** | Build time. Locale-prefixed trees: `docs/en/`, `docs/fr/` | A French reader downloads French prose only |
| **Theme chrome** | Runtime, tina4-js i18n | ~20 short strings, already in the bundle, and `setLocale` re-renders live |
| **Container labels** (Tip/Warning/...) | Build time, from config | They are baked into the HTML by `markdown.js` |
| **Text direction** | Both. `<html dir>` at build, `i.dir()` for live switching | RTL must be right before first paint |

## Scope

### Build-time (content)

- [ ] `config.locales`: `{ root: {label,lang}, fr: {label,lang,link} }`, VitePress-shaped
      so a site can port its config across
- [ ] Locale detection from the first path segment; per-locale `title`,
      `description`, `nav`, `sidebar`, `sectionLabels`
- [ ] `<html lang>` and `<html dir>` per page, replacing today's hardcoded `lang="en"`
- [ ] `<link rel="alternate" hreflang>` between translations of the same page
- [ ] Locale switcher in the header, only rendered when >1 locale is configured
- [ ] Search index carries a `locale` field; search filters to the active locale
- [ ] Container labels (`Tip`, `Info`, `Note`, `Warning`, `Danger`, `Details`) become
      overridable per locale instead of the hardcoded `CONTAINERS` map in
      [src/markdown.js](tina4press/src/markdown.js)

### Runtime (theme chrome, tina4-js)

- [ ] Extract every hardcoded UI string into a default `en` bundle. Full list:
      "On this page", "Edit this page", "Search", "Search the docs...",
      "Type to search the docs...", "No results.", "navigate", "open", "close",
      "Menu", "Toggle theme", "Copy code", "Permalink", "Overview", "More",
      "Ask", "Ask a question...", "Sources",
      "Sorry - the assistant is unreachable right now."
- [ ] Emit the active locale's chrome bundle inline in the page (it is ~20 short
      strings; a second network round trip for that is not worth it)
- [ ] Wire `createI18n` in [src/theme/client.js](tina4press/src/theme/client.js) and
      replace the literals with `t()` calls
- [ ] Use `i.dir()` so a live locale switch flips direction without a reload
- [ ] Sites can override any chrome string via `themeConfig.messages[locale]`

## Deliberately NOT doing

- Translating content at runtime. Prose is build-time, always.
- A translation-management integration. A JSON file per locale is enough.

## Tests

- [ ] `i18n: a page under /fr/ gets lang="fr" and the French nav`
- [ ] `i18n: an untranslated key falls back to the root locale, then the key` (negative)
- [ ] `i18n: an RTL locale sets dir="rtl" on <html>`
- [ ] `i18n: hreflang alternates link the same page across locales`
- [ ] `i18n: the switcher is absent when only one locale is configured` (negative)
- [ ] `i18n: search results are scoped to the active locale`
- [ ] `i18n: container labels follow the page locale`

## Risks

- The chrome bundle inlined per page adds roughly 400 bytes to every page. Measure
  it; if it grows past ~1 KB, move to a fetched bundle for non-root locales only.
- `detectLocale()` in tina4-js reads `navigator.language`. For a static site the URL
  must win over the browser, or a reader gets a language the URL did not promise.
  Pass `locale` explicitly from the build; never let it auto-detect.

Two bugs the tests caught: the locale direction collided with `config.dir` (the
site root path), putting a filesystem path into `<html dir>`; and `build()`'s
`quiet` option forced `ok:true`, hiding broken links from a quiet caller.

## Divergence from the original design

The plan said to wire tina4-js's reactive i18n for live locale switching. Built
differently on purpose: switching locale on a static site is NAVIGATION to a
different page tree, not state, so a reactive locale signal would be code
earning nothing. Chrome strings resolve at BUILD time; tina4-js's `t()` is used
only for the handful of strings JavaScript produces at runtime.
